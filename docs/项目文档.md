# 大肥鱼 QQ 聊天机器人 项目文档

> 本文按《软件工程导论（第 6 版）》的开发阶段组织：可行性研究 → 需求分析 → 总体（概要）设计 → 详细设计 → 编码与测试 → 运行维护。

## 1. 可行性研究

### 1.1 项目目标

做一个能长期运行在自己电脑上的 QQ 聊天机器人「大肥鱼」：性格活泼可爱、知识面广，能在私聊和群聊中自然聊天，记住聊过的事，成本可控，数据留在本地。

### 1.2 接入方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 腾讯官方 QQ 机器人 | 合规、稳定、无封号风险 | 群聊必须 @ 才可回复且有 5 分钟窗口、次数限制；主动消息额度很小 | 不适合自由聊天 |
| NapCat + OneBot 11 | 免费、协议完整、可自由收发消息、生态成熟 | 非官方协议，有风控/封号风险；需要常开设备 | **采用**（只挂备用小号） |
| NoneBot / AstrBot 框架 | 插件生态丰富、开箱即用 | 依赖和抽象较重，本项目功能不多，学习与维护成本偏高 | 不采用 |

### 1.3 大模型与开发方式

- 模型：DeepSeek（OpenAI 兼容接口），按量计费，价格低，中文表现好。
- 开发方式：自建轻量 Python 项目（FastAPI + httpx + sqlite3），不引入机器人框架，代码可控、依赖少。

### 1.4 经济可行性

- 软件全部免费、开源依赖。
- 费用只有大模型调用：按官方价格约 1 元/百万输入 token、2 元/百万输出 token，日常家庭/小群使用每月通常几元以内。
- 部署不需要云服务器：家里常开的电脑即可；QQ 消息经腾讯服务器转发，不需要公网 IP。

### 1.5 结论

技术可行、成本可接受、操作门槛低。主要风险是非官方协议带来的账号风险，通过「只用备用小号 + 本地监听 + token 校验」把风险控制在可接受范围。

## 2. 需求规格说明书

### 2.1 功能需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR-1 | 私聊聊天 | 收到私聊消息后调用大模型并回复 |
| FR-2 | 群聊触发 | 被 @、文本包含「大肥鱼/肥鱼」时回复 |
| FR-3 | 群聊默认接话 | 群聊未点名时也默认回复（概率默认 1）；概率与冷却可通过配置调整 |
| FR-4 | 上下文 | 每个会话保存最近若干条消息，作为模型上下文 |
| FR-5 | 摘要 | 未摘要消息达到阈值时自动生成摘要，控制上下文长度 |
| FR-6 | 长期记忆 | 私聊 `/remember` 保存，`/memories` 查看，`/forget` 清空 |
| FR-7 | 重置 | `/reset` 清空当前会话的消息与摘要，保留长期记忆 |
| FR-8 | 指令 | `/help`、`/ping`，群聊中指令需 @ 或叫名字 |
| FR-9 | 分段回复 | 长回复切成最多配置段数，每段不超过配置字数；超出部分并入最后一段，明显超长时才在句末截断 |
| FR-10 | 引用回复 | 群聊首段回复引用原消息（可配置关闭） |
| FR-11 | 限流 | 同一会话最小间隔与每分钟上限，防刷屏 |
| FR-12 | 故障兜底 | 模型调用失败时回复友好提示，不崩溃 |
| FR-13 | 忽略自身消息 | 不响应机器人自己发出的消息 |
| FR-14 | 多媒体理解 | 只发图片/表情/语音且无文字时，组织成模型可读内容并生成回复 |
| FR-15 | 人格语料检索 | 按消息从本地语料库检索相关片段注入提示词（RAG，不是模型微调） |
| FR-16 | 请求不自动审批 | 好友/入群请求只记录日志，一律由号主在 QQ 客户端手动确认 |
| FR-17 | 表情/图片理解 | 表情、表情包、图片交给模型理解并生成回复；图片转 data URL，原生小表情以表情名作为文字说明 |
| FR-18 | 戳一戳回应 | 任意戳一戳事件由模型即兴回应；机器人自身触发除外，受同一限流 |
| FR-19 | 联网搜索 | 把联网搜索注册为模型可调用的 `web_search` 工具，由模型判断是否需要实时信息；需要则调用 DeepSeek Search API 并把网页摘要回传给模型；普通闲聊不搜索，失败不影响聊天 |
| FR-20 | 链接解析 | 消息文字或分享卡片里带链接时，抓取页面文字交给模型：B 站取标题/UP主/时长/播放/简介/标签/热评/弹幕，普通网页取标题/摘要/正文；失败或超过数量上限时跳过，不影响聊天 |
| FR-21 | 语音识别 | 收到语音消息时下载语音文件，silk 用 pilk 解码、amr 等用 ffmpeg 转 wav，调用硅基流动 SenseVoiceSmall 转成文字，以 `[语音转文字]：...` 放进对话；未配置 Key 或失败时只提示 `[语音]` |
| FR-22 | 语音回复 | 模型判断适合语音时在回复开头输出 `[语音]`，程序去掉标记并用 Edge TTS 合成 mp3、以语音消息发送；超过字数上限或合成失败时自动改发文字 |

### 2.2 非功能需求

| 类别 | 需求 |
| --- | --- |
| 性能 | 单条消息处理在模型正常响应下 10 秒内完成；空闲内存占用低；需要联网时额外等待搜索接口（默认超时 15 秒），带语音时额外等待识别（默认超时 30 秒） |
| 可靠性 | 模型失败、网络抖动、WS 断线不导致进程退出；重连后自动恢复；搜索、链接抓取、语音识别与合成失败只记日志，正常聊天不中断 |
| 安全 | WebSocket token 校验；密钥只从环境变量读取；提示词禁止泄露系统设定与隐私；搜索词只发给 DeepSeek；链接解析只允许公网 http/https，拒绝内网主机；语音识别只发给硅基流动，合成走微软 Edge 接口 |
| 隐私 | 语音文件只在本机临时落盘（`data/voice/`，启动清理一天前的文件）；识别需要把音频上传硅基流动，可在配置里关闭 |
| 易用性 | 一条命令启动；配置集中在 `.env`；README 覆盖首次部署 |
| 可维护性 | 模块按职责拆分，核心逻辑可脱离 QQ 单测；日志可定位问题 |
| 成本 | 上下文与摘要机制限制 token 消耗；群聊默认全部接话，但保留每分钟 60 条上限；联网搜索由模型按需触发，每次约 0.005 元（5 元/千次），单条消息最多查 2 次 |
| 兼容性 | Windows 10/11，Python 3.10+；NapCat OneBot 11 反向 WS |

### 2.3 接口需求

1. **外部接口**：NapCat 反向 WebSocket（OneBot 11），路径 `/onebot/v11/ws`，事件上报 + action 调用（echo 匹配）。
2. **模型接口**：DeepSeek `POST /chat/completions`，Bearer 鉴权，非流式。
3. **管理接口**：`GET /health` 返回运行状态。
4. **存储接口**：本地 SQLite 文件 `data/bot.db`。
5. **搜索接口**：DeepSeek Search API `POST /v1/tools/search`，复用大模型 Key，返回网页标题、链接、摘要和发布时间。
6. **链接接口**：B 站公开接口（`/x/frontend/finger/spi`、`/x/web-interface/view`、`/x/tag/archive/tags`、`/x/v2/reply`、`/x/v1/dm/list.so`）与普通网页 HTTP GET；无需登录 Cookie，失败静默跳过。
7. **语音接口**：硅基流动 `POST /v1/audio/transcriptions`（multipart，模型 `FunAudioLLM/SenseVoiceSmall`，需 Key，官方标价免费）；Edge TTS 在线接口（`edge_tts` 库，无需 Key，输出 mp3）。

### 2.4 逆向需求（明确不做）

- 不做主动私聊/群发营销，不自动添加好友，也不自动同意好友请求或入群邀请；所有请求由号主手动确认。
- 不保存或转发他人隐私，不提供医疗、法律等专业结论。
- 不实现多机器人集群、插件市场、Web 管理后台。
- 不支持官方 QQ 机器人 API（另起项目再做）。
- 联网搜索只取搜索引擎返回的摘要，不抓取网页正文，不把搜索词发给 DeepSeek 以外的搜索厂商。

### 2.5 数据需求（数据字典）

| 数据项 | 类型 | 说明 |
| --- | --- | --- |
| chat_key | TEXT | 会话标识：`private:<QQ号>` 或 `group:<群号>` |
| messages.role | TEXT | `user` 或 `assistant` |
| messages.content | TEXT | 群聊用户消息格式为「昵称：内容」 |
| summaries.covered_until | INTEGER | 摘要已覆盖的最大消息 id |
| memories.content | TEXT | 一条长期记忆，最多保留 100 条/会话 |

## 3. 概要设计

### 3.1 总体结构

```
NapCat（QQ 协议端）
        │ OneBot 11 反向 WebSocket
        ▼
app/main.py（FastAPI：接入、鉴权、分发）
        │
        ▼
app/core/engine.py（业务主流程）
   ├── trigger.py   触发判断 + 限流
   ├── commands.py  斜杠指令
   ├── persona.py   人格/提示词（含风堇语气）
   ├── knowledge.py 人格语料检索（读取 knowledge/hyacine.md）
   ├── search.py    联网搜索（DeepSeek Search API）
   ├── link.py      链接解析（B 站视频信息、普通网页正文）
   ├── voice.py     语音识别（硅基流动）与语音合成（Edge TTS）
```

### 3.3 设计原则

- **高内聚低耦合**：事件解析不认识数据库，存储不调用模型，模型不关心 QQ；engine 只做编排。
- **可测试性**：发送端抽象为 `MessageSender` 协议，测试用假对象替换；模型用 FakeLLM 替换。
- **单线程事件循环**：并发来自 `asyncio`，同一会话用锁串行，避免上下文错乱。
- **失败隔离**：任何外部调用失败都在边界处转为日志 + 友好提示。

## 4. 详细设计

### 4.1 消息处理流程

1. 解析事件 → 得到 `MessageEvent`（文本、是否 @、是否含媒体、会话 key）。
2. 清洗文本；若含别名，记录下来并从文本中删除。
3. 群聊里未被 @ 也未叫名字的 `/xxx` 直接忽略，避免打扰。
4. 命中指令条件（私聊 / @ / 别名）时先执行指令，指令不调用模型。
5. 触发判断：私聊/@/别名必回；否则按概率 + 冷却随机接话；再经过限流。
6. 空文本但有表情/图片/语音 → 组织成文字说明或图片内容交给模型生成回复；仅叫名字 → 回复「我在呀」。
7. 取当前会话锁 → 检索人格语料 → 组装 system（人格 + 风堇语气 + 场景 + 摘要 + 长期记忆 + 语料片段 + 搜索工具说明）+ 最近消息 + 当前消息。
8. 带 `web_search` 工具调用模型；模型判断需要实时信息时返回 tool_call，程序按模型给的关键词调用 Search API，把网页摘要作为 tool 结果回传后再请模型生成回复；搜索失败只记日志，聊天继续。
9. 模型或接口不支持工具调用时，退回关键词判断：命中就先把网页摘要塞进 system 提示词，再调用模型。
10. 模型调用失败则用兜底文案且不写库。
11. 成功则写入 user/assistant 两条消息。
12. 分段发送（首段可引用原消息）。
13. 后台异步检查是否需要生成摘要（达到阈值才调用模型）。

### 4.2 触发与限流算法

- 私聊 / @ / 别名：`RateLimiter.allow(chat_key)` 通过即回复。
- 其它群消息：概率 ≤ 0 直接不回复；默认概率为 1（每条都接），否则检查冷却时间，掷随机数命中后再过限流。
- `RateLimiter` 为每个会话维护时间队列：两次回复间隔 ≥ `RATE_MIN_INTERVAL`，最近 60 秒内不超过 `RATE_PER_MINUTE` 次。

### 4.3 上下文与摘要

- 上下文只取最近 `CONTEXT_MESSAGES` 条，天然有上限。
- 当「id > 摘要 covered_until」的消息数达到 `SUMMARY_TRIGGER` 时，把旧摘要 + 新对话交给模型，生成 ≤400 字新摘要，并记录新的 covered_until。
- 摘要表每个会话只保留最新一条，控制数据库增长。
- 摘要任务在后台执行并加会话级摘要锁，避免重复生成。

### 4.4 回复分段

- 先按段落拆，再按句号/问号等标点断句；超长句硬切。
- 相邻小段在不超过 `MAX_REPLY_CHARS` 时合并。
- 超过 `MAX_REPLY_SEGMENTS` 段时，余下内容并入最后一段（不再逐段硬截，避免话说到一半断掉）；只有明显超长（超过单段上限 3 倍）时才在句末标点处截断并加省略号，找不到标点才硬截。
- system 提示词里同时告知「整条回复别超过约 `MAX_REPLY_CHARS × MAX_REPLY_SEGMENTS` 字」，从源头减少被截断。

### 4.5 人格语料检索（RAG）

- 语料放在 `knowledge/hyacine.md`，按 `## 小节标题` 切块；HTML 注释和「使用说明」「资料出处」小节不进入检索。
- 打分方式：问题与语料块去掉标点、转小写后切成 bigram（两字符窗口），用「重叠 bigram 数 / 问题 bigram 数」作为相似度；至少要有 2 个 bigram 重合（问题本身不足 2 个时按实际数量），且相似度不低于 0.12 才算命中。
- 每次取相似度最高的 `KNOWLEDGE_TOP_K` 段（默认 2 段），以「【风堇语料参考】」追加到 system 提示词，每段最多 400 字。
- 这是检索增强生成（RAG），不是模型微调：不改模型权重、不上传语料，只影响当前这一次请求的提示词。
- 语料首次使用时读入并缓存在内存；修改语料后需重启进程生效。

### 4.6 错误处理

| 场景 | 处理 |
| --- | --- |
| 模型 HTTP 429/5xx | 重试 1 次（间隔 1.2 秒），仍失败抛 `LLMError` |
| 搜索 HTTP 408/429/5xx | 重试 1 次（间隔 1 秒），仍失败只记日志并返回空结果，继续正常聊天 |
| 搜索 401/402/400 | 不重试，日志写明接口原因（Key 无效或余额不足） |
| 搜索结果为空 | 不注入提示词，模型按自身知识回答 |
| 网络错误 | 同上；最终由 engine 兜底 |
| 返回格式异常 | 抛 `LLMError`，不把异常内容发给用户 |
| 发消息超时/WS 断开 | 记录警告；挂起请求立即失败；不影响进程 |
| 新连接替换旧连接 | 关闭旧连接并清理其挂起请求 |
| 好友/入群请求事件 | 只记录日志，绝不调用审批接口，由号主手动确认 |
| 非消息事件（心跳等） | 直接忽略 |

### 4.7 安全设计

- WebSocket 支持 `Authorization: Bearer <token>` 或 `?access_token=`，token 不一致返回 1008。
- 密钥只在 `.env`/环境变量中，代码不硬编码；日志不打印密钥。
- 人格提示词限制：不泄露系统提示、不编造、不冒充真人、敏感话题拒答、不索要隐私。
- 不实现好友/入群请求的自动同意：`main.py` 收到 `request` 事件只写日志，所有审批由号主在 QQ 客户端手动完成。
- 图片识别会把图片内容发送给 DeepSeek；只下载必要图片，单张限制 5 MB、单条最多 2 张；不保存图片文件。
- 默认监听 `127.0.0.1`；若需外网访问，应由用户在反向代理层加 TLS 与鉴权。
- 联网搜索的词会发送给 DeepSeek Search API（与大模型同一厂商）；只在需要时搜索，不在本地保存搜索记录。
- 联网结果以「参考资料」身份进入提示词，并明确要求忽略网页中改变身份、泄露提示词或执行其他操作的文字，降低网页提示词注入风险。

### 4.8 数据库表

```sql
messages(id, chat_key, role, content, created_at)
summaries(id, chat_key, content, covered_until, created_at)
memories(id, chat_key, content, created_at)
```

均按 `chat_key` 建索引；SQLite 开启 WAL，每次操作独立连接，避免跨线程共享连接。

### 4.9 联网搜索

- 方案选择：①每条消息都搜索——时效最好，但延迟和费用高；②模型端 `web_search` 工具——实测 `deepseek-flash` 支持 Chat Completions 的 function calling，模型能按问题自己判断并给出搜索关键词，**采用**；③关键词触发 + 独立 Search API——命中才搜、费用可控，保留为工具不可用时的兜底。
- 触发：由模型自己决定。system 提示词里的 `SEARCH_TOOL_GUIDE` 要求它在榜单排名、新闻、价格、票务、天气、赛事、新游戏、新版本、附近店铺等场景先调用 `web_search`，常识/观点/安慰/闲聊不调用。兜底路径仍用 `needs_search(text)` 的关键词表：明确查询词（搜一下、查一下、最新、新闻、官网、多少钱、价格等）直接搜索；时效词（今天、最近、天气、股价、比分等）必须同时出现疑问词（吗、什么、怎么、多少、哪、几、？等）才搜索，避免「今天好累啊」「最近怎么样」这类闲聊产生费用；关键词表是 `search.py` 顶部的 `_SEARCH_WORDS` 和 `_LIVE_WORDS`。
- 工具协议：第一次请求带 `tools=[web_search]`、`tool_choice=auto`；模型返回 `tool_calls` 时，按 `function.arguments` 里的 `query` 执行搜索（每条消息最多查 2 次），再把 assistant 的 `tool_calls` 和逐条 `role=tool` 结果回传，最后不带工具再请求一次拿到正式回复。
- 请求：`POST /v1/tools/search`，`query` 截断到 128 字符，`count=WEB_SEARCH_COUNT`（默认 3），`need_content=false`（只取摘要，不抓正文）。
- 结果：读取 `results` 数组的 `title/url/summary/site_name/date`；缺字段的条目跳过，`date` 取前 10 位；每条摘要最多 300 字，整段结果最多 900 字。
- 注入：工具路径把摘要作为 `role=tool` 消息回传；兜底路径才在 system 提示词末尾追加「联网搜索结果使用方式」和【联网搜索结果】。两条路径都要求模型概括回答、注明来源、不确定就承认，并忽略网页里的指令性文字。
- 失败：`WebSearchClient` 对 408/429/5xx 重试一次，其余错误直接记日志并返回空列表；engine 再兜底捕获异常，保证聊天不受影响。
- 开关：`WEB_SEARCH_ENABLED=false` 时 main 不创建搜索客户端，engine 不做任何搜索调用；聊天与搜索共用同一个 `DEEPSEEK_API_KEY`。

### 4.10 链接解析

- 提取：`extract_links` 用正则从消息文字里取 `http/https` 链接，并读取 `Attachment.url`（只认 `kind=other` 的卡片，跳过图片 URL）；去掉末尾标点、去重、按 `LINK_PARSE_MAX_LINKS` 截断。QQ 分享卡片的链接来自事件解析：json 卡片优先 `jumpUrl`/`qqdocurl`/`source_url`/`url` 字段，xml 卡片优先 `<url>` 节点，都取不到时退回第一个 http 链接。
- 安全：`_is_safe_url` 只允许 http/https、禁止带账号密码的地址，并拒绝 `localhost`、`127.*`、`10.*`、`192.168.*`、`172.16~31.*`、`169.254.*`，避免群里发内网链接让服务器发起请求。
- B 站流程：`b23.tv` 短链先跟随 302 拿到真实地址 → 从地址里取 BV/av 号 → 调 `/x/frontend/finger/spi` 取 `buvid3`/`buvid4` 写入 Cookie（不带设备 Cookie 时接口返回 412）→ `/x/web-interface/view` 取标题、UP主、时长、播放、点赞、分区、发布日期、简介、cid → 并发取标签、热评（`/x/v2/reply`）和弹幕（`/x/v1/dm/list.so`，解析 `<d>` 文本，去重后最多 10 条）。
- 普通网页：GET 页面，限制体积 4 MB、只接受 text/html/xml/json；标题优先 `og:title` 再 `<title>`，摘要优先 `meta description`/`og:description`，正文去掉 script/style/注释和标签、还原 HTML 实体后截取 500 字。
- 注入：抓取结果拼成「【链接内容（程序抓取的页面文字，可能不完整）】+ 每链接一段」，追加到本轮用户消息（有图片时作为多模态的文本块）；system 提示词追加 `LINK_GUIDE`，要求模型把页面文字与视频画面区分开，内容少就承认没看到，不许编造。链接内容不写入聊天记录，避免数据库膨胀。
- 失败：`LinkReader` 对每个链接单独 try/except，任何异常只记 debug 日志并返回空串；engine 再兜底捕获一次，保证照常回复。单链接内容最多 900 字，避免提示词过长。
- 开关：`LINK_PARSE_ENABLED=false` 时 main 不创建客户端，engine 直接跳过；`LINK_PARSE_TIMEOUT` 控制单次请求超时。

### 4.11 语音识别与语音回复

- 事件解析：`record` 段的 `url`/`path`/`file` 依次取第一个可用值作为音频来源（NapCat 多数时候给本地文件路径），`Attachment.kind="record"`；不会把它当链接抓取。
- 识别流程：`VoiceService.transcribe` 读取音频（http 下载限 10MB，本地文件要求绝对路径且存在）→ 按文件头判断格式 → silk 用 `pilk.silk_to_wav` 解码（纯 Python，兼容腾讯前缀）、amr 或未知格式用系统 `ffmpeg` 转 16k 单声道 wav、mp3/ogg/m4a/flac 原样上传 → `POST /v1/audio/transcriptions`（`FunAudioLLM/SenseVoiceSmall`）→ 取 `text` 截断 500 字。
- 上下文注入：`engine._compose_history_text` 把语音附件渲染成 `[语音转文字]：...`（识别失败则为 `[语音]`），随用户消息进入模型与聊天记录；提示词没有额外要求，模型按普通文字理解。
- 自主语音回复：提示词 `VOICE_GUIDE` 要求模型只在短句、撒娇、安慰、情绪明显时把 `[语音]` 放在回复开头。`pop_voice_marker` 只识别开头标记，避免正文里误伤；标记与正文一起清理后再入库。
- 合成与发送：`VoiceService.synthesize` 用 Edge TTS（默认 `zh-CN-XiaoyiNeural`）流式取音频字节，写入 `data/voice/<uuid>.mp3`，返回绝对路径；`OneBotConnection.send_group_record/send_private_record` 把路径转成 `file://` URI，放进 `record` 段发送，群里首条仍按 `QUOTE_REPLY` 引用原消息。
- 降级：未配置 `SILICONFLOW_API_KEY` 时 ASR 直接关闭；回复超过 `VOICE_TTS_MAX_CHARS`、合成失败、发送失败都退回分段文字，消息不会丢。
- 依赖：Python 新增 `edge-tts`（合成）与 `pilk`（silk 解码），系统新增 `ffmpeg`（amr 等转码），部署脚本已包含；均走国内镜像安装。

## 6. 运行维护

- **启动**：`python run.py`；日志输出到控制台。
- **数据备份**：定期复制 `data/bot.db`（以及 WAL 文件）到其它磁盘。
- **升级**：替换代码后先跑 `pytest -q`，再重启；数据库表结构向后兼容。
- **清理**：`/reset` 清会话上下文，`/forget` 清长期记忆；必要时停机删除 `data/bot.db`（会丢失全部记录）。
- **观察指标**：日志中的模型失败次数、摘要失败次数、联网搜索失败次数、链接解析失败次数、语音识别失败次数、语音合成失败次数、WS 断连次数。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| NapCat 非官方协议导致封号 | 小号被封，机器人掉线 | 只用备用小号；不群发、不加好友、控制频率 |
| 大模型费用超预期 | 成本上升 | 群聊默认全量接话，保留每分钟 60 条上限；上下文与摘要压缩；按需调低 `GROUP_REPLY_PROBABILITY` |
| 好友/入群被自动通过 | 号主失去审批控制 | 程序不调用审批接口；README 指引检查 QQ 隐私与加群设置；日志只记录请求 |
| 图片上传第三方模型 | 隐私顾虑 | 单张限 5 MB、单条最多 2 张；README 说明可关闭图片下载逻辑 |
| 提示词注入/诱导泄露 | 泄露设定或隐私 | 提示词边界 + 不存敏感信息 + 不打印密钥 |
| 电脑不能常开 | 家人无法随时使用 | 说明前提；必要时迁移到便宜云主机 |
| 模型幻觉 | 错误信息 | 人格要求不确定就承认；关键事实不轻信机器人 |
| 联网结果不准确或过时 | 回答有误 | 提示词要求核对结果、矛盾时说明不确定；只把摘要作参考 |
| 联网搜索费用增加 | 成本上升 | 搜索由模型按需触发且单条最多 2 次；`WEB_SEARCH_COUNT` 默认 3；不需要时设 `WEB_SEARCH_ENABLED=false` |
| 链接内容误导或抓取失败 | 回答偏差、延迟增加 | 提示词要求区分页面文字与视频画面、内容少就承认；单链接 900 字上限、最多 2 个链接、10 秒超时；失败静默跳过，可设 `LINK_PARSE_ENABLED=false` |
| 群友发内网链接 | 服务器被探测内网 | `_is_safe_url` 拒绝 localhost 与私有地址段；只允许 http/https |
| 语音上传第三方识别 | 隐私顾虑 | 只在收到语音时上传，单条限 10 MB；识别结果只存本地数据库；介意可设 `VOICE_ASR_ENABLED=false` |
| Edge TTS 属非官方接口 | 微软改接口后合成失败 | 合成失败自动改发文字，消息不会丢；日志记录失败次数；如需稳定可换其他 TTS 并保留同样接口 |
| QQ 语音格式差异（silk/amr） | 转码失败导致听不了 | 按文件头选择 pilk 或 ffmpeg；转码失败只记日志并退化为 `[语音]`；服务器部署脚本已装 ffmpeg |
| 语音回复被滥用刷屏 | 群里连续语音打扰 | 超过 `VOICE_TTS_MAX_CHARS` 不发；提示词限定只在短句/情绪场景用；可用 `VOICE_TTS_ENABLED=false` 关闭 |
| 多人共用同一机器人 | 上下文串台 | 以 chat_key 隔离私聊与各群；记忆按会话分开 |
