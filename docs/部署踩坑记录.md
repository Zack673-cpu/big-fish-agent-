# 云服务器部署踩坑记录

> 记录一次在阿里云轻量服务器（Ubuntu 24.04 / 2 核 1 GiB）上部署本项目的完整过程，把踩过的坑写清楚。下次部署、换机器或排查同类问题时先看这里。
> 部署脚本见 `deploy/linux/install-1g.sh`。

## 环境

- 阿里云轻量应用服务器，Ubuntu 24.04，2 vCPU / 1 GiB / 30 GiB，华中1（武汉）
- 默认登录用户是 `admin`（不是 `root`，也不是 `ubuntu`）
- NapCat 用官方 Shell 脚本直装到宿主机（不走 Docker）

## 坑 1：SSH 私钥的密码短语被写成了字面 `""`

**现象**：`ssh -i key ... admin@host` 一直 `Permission denied (publickey)`。可服务器 `authorized_keys` 里的公钥指纹完全一致，`sshd -T` 也允许 `ssh-ed25519`，`sshd` 日志里只有 `Connection reset ... [preauth]`。

**根因**：生成密钥时用了 `ssh-keygen -t ed25519 -f key -N '""'`，PowerShell 把 `""` 当成**两个双引号字符**写进了私钥作为密码短语。公钥本身没加密、能正常发送，但服务器发来挑战后客户端没法签名，于是认证失败——表现为"公钥不对"，实际是私钥用不了。

**正确做法**：
- 生成后立刻验证：`ssh-keygen -y -f <私钥>`。直接输出公钥 = 未加密；提示输入密码 = 加密了。
- 需要空密码短语时用 `ssh-keygen -p -f <私钥> -P '""' -N ''` 重设，或在 `cmd /c` 下调 `ssh-keygen` 避开 PowerShell 引号问题。

**排查顺序**：先查本地私钥，再看服务端。这次先怀疑服务器签名算法、又查公钥写入、又查 sshd 配置，绕了一大圈，病根在自己电脑上。

## 坑 2：`install-1g.sh` 默认传 `--github-proxy auto`

**现象**：安装脚本一启动就退出：`错误: --github-proxy 需要 HTTP(S) URL 或 0`。

**根因**：NapCat 官方 `install.sh` 的 `--github-proxy` 只接受 URL 或 `0`，不接受 `auto`。

**正确做法**：默认值改成 `0`（直连），需要加速时显式传完整 URL。

## 坑 3：只给 NapCat 本体加加速前缀，没给 install.sh

**现象**：传了加速站仍然 `curl: (56) Connection reset by peer`。

**根因**：脚本只把加速前缀拼在 NapCat 资源地址上，**下载 install.sh 本身**还是直连 `raw.githubusercontent.com`。

**正确做法**：加速前缀要同时作用于 `install.sh` 与资源下载（脚本里已用 `NAPCAT_SCRIPT_URL` 拼接）。

## 坑 4：`ghproxy.net` 下载 34 MB 的包只有 17 KB/s

**现象**：下到 1.2 MB 左右超时中断，`HTTP/2 stream error`。

**根因**：加速站对 release 大文件限速。

**正确做法**：准备多个加速站，先测速再选：

```bash
for p in https://ghproxy.net https://gh-proxy.com https://ghfast.top; do
  printf "%s -> " "$p"
  curl -s -o /dev/null -w "%{http_code}\n" --max-time 12 \
    "$p/https://raw.githubusercontent.com/NapNeko/NapCat-Installer/main/script/install.sh"
done
```

本次 `gh-proxy.com` 成功。

## 坑 5：NapCat 配置不在 `~/Napcat/config`

**现象**：`ls ~/Napcat/config` 报目录不存在，白查一轮。

**实际情况**：配置在
`~/Napcat/opt/QQ/resources/app/app_launcher/napcat/config/onebot11_<QQ号>.json`
（新版 NapCat 把 napcat 目录放在 QQ 资源目录里）。

**正确做法**：先 `find ~ -name "onebot11*.json"` 定位，再改。

## 坑 6：NapCat 默认不生成反向 WS 配置

**现象**：扫码登录成功、QQ 在线，但服务器上的 bot 一条消息都收不到。

**根因**：生成的 `onebot11_<QQ号>.json` 里 `websocketClients` 是空数组，NapCat 不会主动连我们的服务。

**正确做法**：手动写入：

```json
"websocketClients": [{
  "name": "bigfish",
  "enable": true,
  "url": "ws://127.0.0.1:8080/onebot/v11/ws",
  "reportSelfMessage": false,
  "messagePostFormat": "array",
  "token": "与 .env 的 ONEBOT_TOKEN 保持一致",
  "debug": false,
  "heartInterval": 30,
  "reconnectInterval": 3000
}]
```

验证：`ss -tnp state established | grep 127.0.0.1:8080` 应看到**双向**连接。

## 坑 7：改 NapCat 配置必须重启，重启会掉登录

**现象**：写完配置 `systemctl restart napcat`，QQ 退回扫码页，需要重新扫码。

**教训**：每次改 NapCat 配置都要付一次"重新扫码"的代价，所以**配置一次写全**再重启，别改一点重启一次；能用 WebUI 热重载的优先用 WebUI。
`bigfish-bot` 重启没有这个代价，可以随便重启。

## 坑 8：`ss` 里看到 `120.241.130.216:8080` 就以为反向 WS 配错了

**现象**：`qq` 进程有一条连到外部 `120.241.130.216:8080` 的连接，被误判成"NapCat 连错了地址"。

**实际**：那是 QQ 客户端自己的连接，与 OneBot 无关。判断反向 WS 是否成功，只看 `127.0.0.1:8080` 的**双向**连接和 bot 日志里的 `NapCat 已连接`。

## 坑 9：用 PowerShell 通过 ssh 传 `python -c` 内联脚本，引号被吞

**现象**：`SyntaxError: invalid syntax`，路径字符串的引号消失。

**根因**：PowerShell → ssh → bash 三层引号剥离。

**正确做法**：复杂脚本不要内联，**本地写好文件再 scp 上去执行**（本次改用 JSON 文件覆盖配置）。

## 坑 10：部署说明里的用户名写成了 `root`

**实际情况**：阿里云 Ubuntu 24.04 镜像的默认登录用户是 **`admin`**（不是 root，也不是 ubuntu）。写脚本提示和文档时要用真实用户名，否则照抄会失败。

## 坑 11：把服务器密码贴进了对话

**教训**：账号密码不要出现在聊天或日志里。已经泄露的要立刻去控制台重置，并优先改用密钥登录。

## 一次正确的部署顺序

1. 本地验证私钥可用：`ssh-keygen -y -f <私钥>`
2. 公钥装到服务器，**立刻**试连：`ssh -i <私钥> <用户>@<IP> 'echo OK'`
3. 本地打包 → scp 上传 → 服务器解压
4. `.env` 用 scp 传（不要手工输入 Key），`chmod 600`
5. 跑安装脚本；加速地址先 curl 测速
6. 定位 NapCat 配置真实路径：`find ~ -name "onebot11*.json"`
7. **一次性写全**反向 WS 配置 → 重启 NapCat → 扫码
8. 验证：`ss` 看双向连接 + bot 日志出现 `NapCat 已连接`
9. 端到端：群里戳一戳，看 NapCat 日志出现 `发送 ->`
